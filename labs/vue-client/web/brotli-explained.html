02 / misconception

The identifiers are already mangled.

For the final runtime-only bundle, every local binding is one or two characters. Oxc also converts eligible static object["name"] reads to object.name. The build is not losing because functions are called createSomethingVeryLong.

What must stay named: public ESM exports, observable function name/length, plugin-facing AST fields, VNode fields, and dynamic user object properties. Renaming those would make a smaller but incompatible Vue.

03 / dynamic values

What does JsValue cost?

JsValue is correct at dynamic JavaScript boundaries. The problem is using it for internal values whose fields and call signatures are already known.

Vue: direct DOM operations

const transitionClasses = el[vtcKey]
if (transitionClasses) {
  value = (value
    ? [value, ...transitionClasses]
    : [...transitionClasses]).join(' ')
}
el.className = value

VueLil: generic host operations

JsValue transitionClasses =
  hostRead(element, vtcKey);
JsValue classes = hostArrayFrom(transitionClasses);
JS.invoke(classes, "unshift", value);
value = JS.invoke(classes, "join", " ");
hostWrite(element, "className", value);

Why the second shape is harder to optimize

  • hostRead(value, key) accepts any object and any key. A downstream optimizer must assume getters, proxies, or arbitrary behavior.
  • JS.invoke(value, "join", ...) carries a method-name string and receiver plumbing instead of a statically typed method call.
  • Dynamic string keys cannot be safely property-mangled.
  • The helper function and each call add tokens, arguments, and punctuation even after local-name mangling.
Correct usage: keep JsValue for public/user/plugin objects and genuinely computed keys. Use typed LilScript classes, fields, arrays, maps, and typed host interfaces for internal data and static DOM operations.

04 / object shape

Why Vue's class can be smaller than a dynamic object bag.

Vue: one prototype implementation

class RefImpl {
  dep = new Dep()
  constructor(value, shallow) {
    this._rawValue = shallow ? value : toRaw(value)
    this._value = shallow ? value : toReactive(value)
  }
  get value() {
    this.dep.track()
    return this._value
  }
  set value(next) { /* update */ }
}

VueLil today: build each object dynamically

JsValue refValue = hostCreateObject();
write(refValue, "_rawValue", initialRaw);
write(refValue, "_value", initialValue);
write(refValue, "dep", dep);
hostDefineAccessor(
  refValue,
  "value",
  JS.method0(() => hostRead(refValue, "_value")),
  JS.method1((_, next) => { /* update */ })
);

The class stores getter/setter code once on the prototype. The dynamic factory must carry object creation, string-key writes, accessor descriptor creation, and closure construction. The closure source exists once in the bundle, but each runtime ref allocates bound closures and an accessor descriptor. That hurts both size and the measured reactivity workload.

This is why the candidate can contain fewer JavaScript classes but more total functions: runtime-only has 919 functions versus Vue's 443.

04b / helper economics

Do hostCreateMap() and friends help compression?

Sometimes. A helper is a trade: pay once for its declaration, then use a short call at every construction site. After mangling, a() is shorter than repeating new Map. If it is called often enough, it can reduce raw size. Brotli already compresses repeated new Map well, however, so the break-even point for compressed size is different from the raw-byte break-even point.

The important distinction: tiny allocation helpers may be size-positive. Generic operations such as hostRead(value, key), JS.invoke(value, methodName, args), reflection helpers, and rest-argument trampolines are more damaging because they also hide semantics and prevent tree shaking or property reasoning.

Which objective is active?

The LilScript production configurations use priority = "size-first", cost_model = "brotli", identifier/property mangling, and string pooling. gzip-9 is measured, but Brotli-11 is the completion metric. The limitation is scope: the compiler optimizes an individual generated package graph, while Vite later concatenates, tree-shakes, and minifies the application. A helper that wins inside one package can lose after cross-package composition. Final decisions therefore need A/B measurements on the complete reusable application bundle.

05 / observable API repair

What are the Object.defineProperty calls?

Some generated functions do not naturally have Vue's exact public name or length. Build scripts currently repair them after compilation:

Object.defineProperty(local, "name", {
  configurable: true,
  value: "createVNode"
});
Object.defineProperty(local, "length", {
  configurable: true,
  value: 0
});

This is behaviorally important because Vue users and tests can observe createVNode.name and createVNode.length. The issue is where the repair runs. A top-level mutation is a side effect. Rolldown cannot freely delete the function or the mutation, even when an application never imports that export.

Better package shape: emit naturally named functions when possible. For unavoidable repairs, isolate each export in a tree-shakable module so importing ten Vue functions does not retain descriptor mutations for the other 136.

06 / hot path

Renderer trampolines multiply calls.

Vue: fixed-signature closure

const patch = (
  n1, n2, container,
  anchor = null,
  parentComponent = null,
  parentSuspense = null,
  namespace,
  slotScopeIds = null,
  optimized = !!n2.dynamicChildren,
) => { /* patch directly */ }

VueLil today: rest-array adapter

this.patchFn = JS.methodRest((_, args) => {
  state.patchFromArgs(args);
});

void patchFromArgs(JsValue args) {
  JsValue anchor = null;
  if (rendererLength(args) > 3)
    anchor = args[3];
  // unpack every argument, then call patch
}

The adapter allocates or handles an argument array, performs length checks and dynamic indexing, and makes another call before entering the hot method. Runtime-core creates multiple adapters for patch, unmount, move, mount, children, block children, and render effects. Fixed typed callable fields can preserve the exact external renderer-internals object while keeping the hot implementation direct.

07 / package topology

Open-world does not mean unmangled.

Open-world means a reusable package is compiled without knowing which exports a future application will import. Private names can still be mangled. Public exports must remain stable.

08 / no-compiler plan

What to change in VueLil first.

  1. Publish one reusable mangled package. Remove scenario-specific export selection from final evidence and preserve public names.
  2. Preserve ESM owner modules. Let Vite remove unused files instead of flattening the complete package into one side-effectful module.
  3. Separate production and test graphs. Keep test exports, warnings, source maps, and compatibility initialization out of production artifacts.
  4. Make reflection tree-shakable. Repair function reflection only in modules whose exports survive.
  5. Use typed internal classes. Start with refs, computed refs, dependency links, and deps.
  6. Use fixed collection helpers. Replace string-dispatched generic Map, Set, and Array calls on hot paths.
  7. Remove renderer rest trampolines. Keep the public dynamic internals façade, but use fixed typed calls behind it.
  8. Use typed DOM host interfaces. Keep generic helpers only for computed keys and genuinely dynamic user objects.
  9. Use typed internal enum constants. Preserve exported enum objects while eliminating repeated dynamic bag lookups.
  10. Remeasure after every tranche. Require all compatibility tests, matching checksums, reusable-package module audits, and canonical Brotli-11.
Not recommended: renaming public exports, changing Vue algorithms, hiding adapter bytes, relaxing scenarios, or tuning Brotli dictionaries before reducing retained code.
