## What it asks, point by point

1. Progress lives in one simple to-do file, and the history of past batches in another. Keep an agent's context small while migrating. Done the same evening: `docs/migration/index.md` is the progress, `plan.md` the plan and `history.md` the records.
2. The budget model of M3.5 may be over-engineering. Approved on 2026-09-28 as architecture amendment AM1: budgets are counts, and the work-unit currency, tariff, exchange rate, lockstep objectives, gzip shadow and speculative parallel search are dropped or deferred.
3. Beat every competitor. LilScript is typed by design and everything in it is statically analyzable, so decisions come from types, facts and exact rules first (law L22).
4. Implement the whole plan, by design, one heavy job at a time. Verify after each batch of changes, not after every change.
5. The end result must be smaller under each objective: gzip, Brotli and raw.
6. Size is the first priority, compile time the second; the effort level trades them. Levels below the default may be faster and a little larger. The default level 13 and every level above it must never deliver larger output because of a change, apart from rare, very small deviations that a heuristic search of an NP-hard problem cannot avoid. From 13 up, each level tries more, toward the global optimum. Recorded as architecture amendment AM2.
7. Compile time is not a number of seconds. A program that grows takes longer, so a target in seconds either blocks honest growth or says nothing about a new program. Judge compile time by how it scales with the program and by the bytes it buys, relative to the previous binary on the same input. Recorded as architecture amendment AM3; the plan's gates, M3.5's exit, step 6's exit, CP2 and M12.4 follow it.
8. Test less often and move faster: about every 20 minutes of work, or right after a critical part, rather than after each change. Track changes systematically, so an unexpected result in a batch of many changes points to the one that caused it. Recorded in plan rules 5 and 8: a numbered change list per batch, one commit per change, bisected when a batch surprises.
9. The types are guarantees, and the runtime carries no conversion the source did not write. Only explicit forms emit code: a type test (`v is C`, and `as?` when it lands) compiles to `instanceof` or `typeof`, and an explicit conversion (`string(v)`, `float(v)`) to its coercion; `v as T` is a trusted view with no code. This is the substance of owner question Y1 (R1, trusted crossings), answered yes: no coercion at crossings and no normalization at loads, which is M10.12's work. Batch S1's syntax already follows it.
