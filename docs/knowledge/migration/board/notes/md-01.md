# md-01 — The react-markdown stack must beat Terser/Oxc on Brotli-11

Parent: [ledger](../LEDGER.md). Status: active.

## Question

The `@itslil` react-markdown stack (unified → micromark → remark → rehype → katex)
loses Brotli-11 to `terser(official graph)` on seven of sixteen packages. Where do
the bytes actually go, and which of it is the compiler's fault rather than the
ports'?

## Current hypothesis

Three separate causes, in descending size, established by measurement rather than
by reading the previous session's numbers:

1. **LilScript leaves optimization on the table that Terser finds in its own
   output.** Running Terser over an artifact LilScript already emitted is not
   supposed to shrink it; across the stack it shrinks it by **42,787 Brotli**.
   That is the compiler losing to Terser by its own definition. The single
   largest named pass is `collapse_vars` (value placement), worth −253 Brotli on
   micromark alone; `unused` and `side_effects` follow.
2. **Two ports embed unminified vendored JavaScript.** `rehypelil` bundles
   `parse5-host.js` (lines 4–7833 of a 9,897-line artifact) and `errors-host.js`
   verbatim; `rehype-katexlil` vendors 387 KB of raw `.js`. Only the last 1,745
   lines of `rehype.esm.js` are compiler output. This is most of rehype's +9,237
   and rehype-katex's +38,884.
3. **`katexlil` does not compile, and its shipped artifact is not valid
   JavaScript.** Three independent codegen faults, none caught by
   `analyze_generated_javascript`.

## Constraints specific to this task

- The fix for (1) must be a general compiler improvement, never a per-library
  special case — see [no-library-specific-optimizations].
- (2) may not be solved by post-minifying the artifact: the objective admits
  compiler output only.
- Brotli-11 from `target/release/lilscript-codec` is the score. Raw is diagnostic.

## Resolved miscompile — a stored argument was deleted with its container

`remark-gfm` emitted `{document:{},text:{}}` for `gfmFootnote()`: every construct
in the extension was deleted, so `[^x]` parsed as a `linkReference`. Silent — no
error, no failing gfm test, only three failures four packages downstream.

**Cause.** `unobserved_local_mutables` (`src/optimizer.rs`) decides which locally
allocated mutables are never observed, so `eliminate_dead_control_flow_instructions`
may drop stores into them. For a direct call whose result is unused and whose
callee only mutates its arguments, it recorded a *mutation group* built from
`summary.mutated_parameters` alone — and observed **none** of the arguments. So
`pinCode(document, 91, def)` linked `document` but never `def`. Once `document`
was observed the group made `document` observed, `def` stayed unobserved, and the
store — plus the tokenizer closures reachable only through it — was deleted.

The `ArrayPush` / `MapSet` arm immediately below observes every argument, which is
the correct discipline; the `CallDirect` arm was the one that did not follow it.

**Fix.** `FunctionEffectSummary` now carries `retained_parameters` — the
parameters a call may *keep*, computed from the stores in its body and propagated
through calls in the same fixpoint that already computes `mutated_parameters`.
Only those join the mutation group, so observing the container observes what was
put in it. The first attempt grouped *every* argument, which is also correct but
pins the keys and scalars a helper merely reads; asking the summary instead costs
nothing on the markdown stack and is the relation the analysis should have had.
Test: `a_stored_argument_is_observed_with_the_container_it_is_stored_in`.

**How it was found**, for the pattern rather than the instance: bisect the
optimizer by pass, then bisect the *input* until the trigger is minimal. It needed
`gfmTable()` present only because two large sibling functions in one caller changed
the effect summaries; the reproduction reduces to one helper, one container and one
stored object.

## The state-machine cliff — largest single win so far

`can_structure` is all-or-nothing: one branch that is not the header of a
recognised `ControlShape` and the **whole function** is emitted as
`let a=0;for(;;)switch(a){case 0:…a=1;continue;…}`.

`remove_unreachable_control_flow` was feeding it broken input. An `if`/`else`
whose arms **both terminate** has no path to its merge block, so plain
reachability deletes it; the shape then fails to remap, because the remap
requires all four of `header`/`then`/`else`/`merge` to survive, and it is
discarded. The branch is now unshaped and the function falls off the cliff.

`if(c){return a}else{return b}` — as ordinary as JavaScript gets — compiled to a
state machine. Minimal case:

```
export JsValue f(JsValue a){ if(a.truthy()){return 1;} else {return 3;} }
before: var W=b=>{let a=0;for(;;)switch(a){case 0:a=!!b?1:2;continue;case 1:return 1;case 2:return 3}}
after:  let W=a=>!!a?1:3
```

katex had 61 such functions and 953 dispatch edges; every other artifact in the
stack had none, which is why this went unnoticed — micromark's port writes
`if (x) { return a; } return b;` and never trips it.

**Fix:** `reachable_blocks_keeping_joins` keeps the join of a surviving `if`/`else`
alive, so the shape remaps and the function stays structured. Regression test
`a_two_armed_if_whose_arms_both_return_stays_structured`. Worth **−8,748 Brotli**
across katex and rehype-katex, byte-identical on marked, corpus unchanged.

## Rejected — `fold_fresh_empty_array_pushes`

`x=[];x.push(a);x.push(b)` → `x=[a,b]` is the array counterpart of the existing
fresh-object fold, and the ceiling is real: on katex's own declaration variant it
folds 895 runs, `.push(` 4,035 → 516, **−29,047 raw and −728 Brotli**.

It is not landed, for three reasons measured in that order:

1. **`Array.prototype.push` honours an inherited index setter; an array literal
   does not.** `preserves_pushes_observable_through_inherited_array_setters`
   already pins this. The fold is therefore only legal under
   `assume_pristine_builtins`, which the peephole does not currently receive —
   plumbing it through is ~6 call sites and was done, then reverted with the
   fold.
2. **The katex win never reaches the artifact.** The peephole's own output is
   −728 Br and the shipped bytes do not move: the declaration variant it is
   handed is discarded further down, so every rewrite on it is thrown away. The
   cause of *that* is the next section and is worth more than this fold.
3. **Partial application costs Brotli**, the same lesson as the statement folds.
   Net −179 Br across the markdown stack but **+26 on jQuery**, which the
   standing constraint forbids.

Land it when (2) is fixed and it can be measured at full coverage on katex.

## An invalid declaration variant is silently discarding all peephole work

katex's array-push runs fold cleanly — 895 runs, `.push(` 4,035 → 516,
275,727 → 246,680 bytes, **−728 Brotli on the candidate** — and the shipped
artifact does not change at all.

The candidate is thrown away, and not on score. The declaration variant the
peephole is handed already contains

```
h>0&&a+=.25
```

which is not valid JavaScript: `&&` binds tighter than `+=`, so this is an
assignment to an rvalue. It needs `h>0&&(a+=.25)`. Both the peephole's input and
its output carry it, `analyze_generated_javascript` accepts it — the token
validator cannot see precedence — and something downstream rejects the leaf, so
the compiler falls back to a baseline that never saw the peephole.

The shipped artifact is valid, so this is not a correctness bug in what ships. It
is worse in a quieter way: **every parsed-peephole rewrite on that variant is
discarded**, and the only symptom is an artifact that is mysteriously larger than
the candidate the compiler measured. On katex that is 728 Brotli of proven,
already-computed improvement thrown away.

**The `&&` emission is fixed** (below), and katex's artifact still does not move,
so that construct was not the only thing wrong with the variant. Finding the rest
is the highest-value remaining compiler task: it is proven, already-computed
improvement being discarded. It also argues, again, for a grammar-complete check
over the emitted subset — a token validator that accepts `a&&b+=c` cannot tell
the compiler which of its candidates are real.

### Fixed: an `&&` operand that binds looser is now grouped

`AND_LHS_NEEDS_WRAP` / `AND_RHS_NEEDS_WRAP` were hand-kept lists naming plain `=`
and none of `+=`, `-=`, `*=`, … , so `if(h>0)a+=.25;` folded to `h>0&&a+=.25`.
Both lists are replaced by the precedence relation the repo already has —
`binary_operator_tightness` — which asks whether the operand binds looser than
`&&` and is correct for the whole family at once, `=>` included. `**=` was also
missing from that table and is added. Regression test
`an_and_operand_that_binds_looser_is_grouped`.

## Candidate search is on — `search-01` unblocked for this stack

`candidate_search` was `off` on every port here. It is now `always` on **fifteen
of sixteen**, each gated by that port's own suite, and it is the single largest
size lever found: **remark-gfm flips from +156 to a −211 win**, remark −1,035,
katex −1,528, to-html −457, to-hast −538, rehype-stringify −431, remark-rehype
−470, unified −205, remark-math −229.

Getting there meant fixing **three compiler bugs**, each of which search exposed
and each of which is real outside it:

1. **`class X extends push`.** `infer_base_from_ctor_call` scanned a constructor
   for any `IDENT.call(this` and took `IDENT` as the base. In
   `Array.prototype.push.call(this.fns, r)` it matched `push` — the tail of a
   member chain, naming no binding — and the receiver was `this.fns`, not `this`.
   `ReferenceError: push is not defined`. The base must be a standalone binding
   *and* `this` must be the receiver. `constructor_leading_base_call` had the
   same second defect.
2. **A fluent method fused into a class.** `return this` was the fold's evidence
   of a constructor, but a chainable method returns `this` too — unified's
   `freeze()` and `use()` both do. Every call site then threw `Class constructor
   cannot be invoked without 'new'`. A `new` site or a `.prototype` touch is now
   required as positive evidence.
3. **A beta-reduced conditional lost its parentheses.**
   `fold_identity_arrow_iife` reduces `(c=>BODY)(x)` to `BODY`, dropping the
   group the call expression provided. `beta_reduction_needs_grouping` checked
   the following token for member and binary operators but not `?`. Since `?:`
   is right-associative, `(c=>a?b:d)(x)?e:f` became `a?b:d?e:f` — unified's
   `process` discarded every string its compiler produced and its promise never
   settled. Reproduces in 18 lines of `.lil`; the guard now asks the precedence
   table, as the `&&` fix does.

`react-markdown` is the one port still on `off`, and its failure is the genuine
`ident-05` shape rather than a fourth unrelated bug. Under search the artifact
parses, has no unbound store, and still throws `r is not a function`: inside an
inlined IIFE `r` is called as the `Info` factory, while in the enclosing scope
`r` holds a property value (`…})(l,n);if(r!=null&&…`). A local shadows an outer
binding the nested body still needs.

`validate_resolved_generated_bindings` cannot see this. It rejects a name *bound
as a non-enclosing function local* — a read that resolves nowhere — but a read
that resolves to the **wrong, nearer** binding type-checks fine at every level.
Closing it means the renamer must refuse a local name that shadows an outer
binding referenced by the function or any closure nested in it, which is the
`local_mangler` / `collect_top_level_references` machinery that `cross_scope_name_reuse`
already uses. That is the remaining `ident-05` work, now with a concrete
reproduction. `remark-breaks` needed no
compiler change — its test pinned the double-quote spelling of `"type"` while
search picks single quotes, so the assertion now matches either quote and still
pins the data.

## Value placement: the hand-list is gone, the win is not there

`fold_statement_assignments_into_first_use` decided whether an assignment could
move to its first read by consulting a hand-kept list of "inert" prefix tokens
that omitted identifiers, `&&`, `?` and much else — so it stopped at the first
ordinary expression and almost never fired. That is now the actual question:
*can anything evaluated before the read observe the value?* Bindings, literals
and pure operators cannot; a call, a property access (getter), an assignment or
an update can.

**It changed nothing on this stack.** All sixteen artifacts are byte-identical
and the corpus is unchanged, so this is a correctness-of-form change, not a size
win — recorded that way deliberately. The fold is a scored late pass, so where it
does fire the objective still decides.

`collapse_vars` remains Terser's top named pass on micromark at −241. Closing it
needs the soundness condition over an expression tree — reachable value, no
intervening observation — which the token stream cannot express. That is the
`ident-02` debt and it is the honest next step for the micromark family.

## rehype-katex: the HTML round-trip was the whole gap

`rehype-katex` rendered KaTeX to an HTML **string** and then parsed that string
back into hast — which is why it bundled 387 KB of `parse5` +
`property-information` + `vfile` to obtain a single function,
`fromHtmlIsomorphic`. Official `rehype-katex` has to do that, because
`katex.renderToString` is the public API it is given.

We are not given it — we own both sides. `__renderToDomTree` returns the very
tree that `renderToString` serialises (`renderToString` *is*
`renderToDomTree(…).toMarkup()`), and that tree already carries `classes`,
`style`, `attributes` and `children`. `src/dom-to-hast.lil` (≈210 lines) walks it
straight into hast, mirroring `toMarkup` field for field so the result serialises
identically:

- `classes` → `className`, filtered and split as `createClass` does
- `style` → the hyphenated declaration string, with `SymbolNode`'s `italic`
  written first as `margin-right:…em;`, ahead of the style object
- `SvgNode` writes `xmlns` before its attributes, because hast serialises
  properties in insertion order
- a `SymbolNode` with neither class nor style is a bare text node, exactly as its
  `toMarkup` decides

**146,564 → 83,811 Brotli**, against official's 112,877 — from +33,687 to
**−29,066**, a 62,753 swing, with the entire vendored HTML parser deleted and
16/16 official tests green.

The general lesson: a port that reproduces the *public API dance* of the original
inherits its dependencies. Converting between two representations we already
control is smaller and faster than serialising to text and re-parsing it.

## `JS.array` now takes its elements — the language could not express an array literal

katex's source builds **3,930** arrays as `JsValue a = newArray(); JS.push(a, x);`
and the artifact carries 4,035 `.push(` against official's 114. That is not a
style choice: `JS.array()` accepted **zero** arguments, so there was no way to
write a `JsValue` array literal at all. `JS.object` has always been variadic;
`JS.array` now is too, and lowers straight to `ControlFlowOp::Array`, which
already carried its elements.

```
JS.array("accent-body", "x")   ->   ["accent-body","x"]
```

This is the exit the standing rule prefers — improve the language so the pattern
is expressible — rather than a compiler fold compensating for a spelling. It also
sidesteps the semantics question that blocked the fold: `Array.prototype.push`
honours an inherited index setter and an array literal does not, so the fold was
only legal under `assume_pristine_builtins`; a literal written as a literal needs
no such contract. Test: `js_array_takes_its_elements`.

## The `.lil` source is a real, measurable part of the gap

Comparing our source against the original JS per functional area, not just the
emitted artifact:

| area | official JS | our `.lil` | ratio |
|---|---|---|---|
| CommonMark constructs | 65,876 | 182,147 (`core/` + `block` + `inline` + `rules`) | **2.8×** |
| tokenizer plumbing | 41,770 | ~110,000 | **2.6×** |

Not all of that survives compilation — the emitted program does ~23% more named
operations, not 180% more — but the residue is real and the compiler cannot
recover it.

**What is already recovered, and is not worth touching:** the port writes
`call1(objGet(effects,"consume"), effects, code)` where the original writes
`effects.consume(code)` — 436 sites against a single `JS.invoke`. The compiler
fuses every one of them back to `o.m(…)`; only 23 legitimate `.call(` survive,
and the artifact makes **fewer** method calls than official (101 `.consume(` to
its 177). Rewriting those would gain nothing.

**The state bag looked like the lever and is not.** Thirty
`JsValue st = JS.object()` bags with 194 reads and 192 writes survive into the
artifact as property access (`s.size`, `s.limit`) where the original has plain
locals (`let balance = 0`). Converting `factory-destination.lil` to captured
locals and forward-declared closures is **−114 raw and only −2 Brotli** on the
shipped artifact. Thirty modules of that is roughly −60 Brotli — noise. Brotli
already compresses the repeated `s.field` access; the raw saving does not
survive the codec, which is the same lesson as string pooling and the host
wrappers.

It also **broke micromark**: 1,927/1,927 → 1,901/1, the streaming test, state no
longer persisting across chunks. That reproduces with a careful hand conversion,
not just a mechanical one, while minimal repros of forward-declared mutual
recursion compile correctly. The converted file is kept at
`scratchpad/fd-converted.lil` as a reproduction if the capture path is ever
investigated; it is **not** worth pursuing for size.

So the source *is* 2.8× the original, and that ratio is real — but the specific
patterns that make it so (host-call spelling, state bags) are either already
recovered by the compiler or cost nothing under Brotli. Raw size and Brotli size
disagree here, and Brotli is the objective.

## The objective should pick the representation — and `optimization_level` stops it

The compiler already has the right idea: candidate search scores whole artifacts
on the configured codec and keeps the winner. Representation choices — a struct
laid out as an array, a constructor table fused to a class, `var`/`let`/`const`
spelling, function layout — are supposed to be decided that way rather than by a
fixed rule.

They mostly are not, for a structural reason. `optimization_level` is a coarse
outer gate that turns whole families on or off **before** anything is scored:

| level | families first enabled |
|---|---|
| 12 | `SwitchLoweringVariants`, `CaptureSignatureCloning` |
| 13 | **`JointRepresentationSearch`**, `FunctionLayoutVariants`, `IdenticalFunctionFolding` |
| 14 | `IrCompressPassVariants`, `IrPhaseOrderingVariants`, `IrFunctionSubsumptionVariants`, `JointChunkSymbolSearch` |

Every port in this stack ran at **12**, so the representation-search families had
never been reachable at all. Raising the level is not uniformly good, which is
the point: measured per port on Brotli-11,

- **13 wins**: micromark −53, react-markdown −42, remark-rehype −22, unified −11,
  to-hast −10, remark-breaks −7
- **13 loses**: remark-gfm +141, remark +63, rehype-stringify +12, remark-math
  +10, from-markdown +7, to-html +2
- **13 miscompiles**: `remark-parse` (2 tests), `rehype` (53 tests)

Each port now carries the level that measures best under its own suite. That is
the right answer *for the configs*, but it is the wrong shape for the compiler:
the level gate decides membership without consulting the objective, and the
objective-scored search then only ranks whatever the gate let through. A family
that would pay on this artifact and lose on that one is exactly what the search
exists to decide — so family membership belongs inside the scored search, not in
front of it. That, plus the artifact-scaled probe budget that starves large
modules, is why proven improvements keep failing to reach artifacts.

## Property names: measured ceiling, and why the compiler will not take it

The emitted artifacts carry their internal property names in full. micromark's
open and closed artifacts are **byte-identical in their property census** — 187
distinct names, 12,409 bytes — so the closed lane, which is documented to be
allowed to mangle extern keys, mangles none of them.

Renaming every non-builtin key textually in the finished artifacts bounds the
prize:

| package | Brotli now | keys renamed | Brotli | delta |
|---|---|---|---|---|
| katex | 71,674 | 452 | 69,985 | −1,689 |
| rehype | 63,496 | 782 | 61,175 | −2,321 |
| remark | 37,512 | 311 | 36,523 | −989 |
| remark-parse | 27,571 | 201 | 26,775 | −796 |
| from-markdown | 27,491 | 201 | 26,745 | −746 |
| micromark | 26,683 | 147 | 25,972 | −711 |
| remark-math | 2,356 | 33 | 2,255 | −101 |
| **total** | | | | **−7,353** |

**This is an upper bound and it is not safely achievable in full.** The
artifacts were never executed under the renaming. micromark looks its
constructs up by computed key (`constructs[code]`, `handlers[type]`), and the
keys of those tables are exactly the names in the list, so a blind rename
breaks them. Any real mangler needs points-to, not a name census.

### Why the existing mangler declines

`mangleable_internal_js_key` (`src/codegen_ir_js.rs`) gates a `JsValue` key on
a **naming convention**:

```rust
name != "__proto__" && name.ends_with('_') && is_js_property_identifier(name)
```

No port uses that suffix, so no `JsValue` key is ever renamed, in either world.

Replacing the convention with the escape analysis does not help either.
`LILSCRIPT_TRACE_PROPERTY_ESCAPE` classifies every key by the worst escape
state of its receivers; on micromark:

```
local-only 0 keys / 0 bytes | typed 0 keys / 0 bytes
untyped 213 keys / 5,171 bytes | key-opaque receivers 406
```

All 213 escape. That verdict is defensible: a construct's state functions are
handed to the tokenizer loop as `JsValue`, so the values really are reachable
from an untyped boundary. `value_escapes` is also the wrong question — a
closure that escapes does not expose the *keys* of what it captures. Key
visibility is a weaker property than value escape and would need its own
reachability analysis over allocation sites.

### Typed internals do not pay for themselves

The standing objective says internals should use Lil classes so the compiler
can choose a representation. `src/core/html-text.lil`'s `st` bag is the ideal
case — created with `JS.object()` inside a closure, eight fields, never
returned. Converted to a typed class (1,927/1,927 still green):

| form | raw | Brotli |
|---|---|---|
| `JsValue` bag (baseline) | 90,454 | **26,683** |
| typed class, `positional` | 90,410 | 26,743 (+60) |
| typed class, `named` | 91,117 | 26,730 (+47) |

Positional layout **removed the field names entirely** — `returnState` does not
occur in the artifact — and still lost. Raw fell 44 bytes while Brotli rose 60.
Brotli already pays almost nothing for a repeated long name, and the class
constructor plus index literals cost more than the names did. Both experiments
were reverted.

The lesson generalises past this module: **raw size is not a proxy for the
objective here, and neither is name length.** A representation choice must be
scored on the configured codec or not made at all. `aggregate_layout` is a
static flag (`Positional` by default) that the candidate search never scores —
`grep aggregate_layout src/compiler.rs` is empty.

### Why the compiler materialises: the store census

`LILSCRIPT_STORE_CENSUS=1` on micromark (counts accumulate over the search;
the ratio is the signal):

```
unstable=68,673 (53%)   cross_block=29,556 (23%)   use_count>1=28,044 (22%)   single_use=4,767 (4%)
```

`unstable_values` (`src/codegen_ir_js.rs`) is a **transitive saturating taint**:
a value is unstable if its op is observable, cannot be deferred, or *any
operand* is unstable. `op_evaluation_is_observable` makes `IndexGet` observable
whenever the object's coercion category is dynamic — true of every `JsValue` —
so the taint reaches nearly everything, and an unstable value must be
materialised unless it is fused.

Two candidate causes were tested and refuted:

- **`run.len() >= 2` in `operand_order_fusable_values` is not the blocker.**
  Relaxing it to `>= 1` produces a **byte-identical** micromark (1,927/1,927),
  because `can_fuse_value` already nests a producer whose consumer is the
  immediately following instruction. Reverted.
- **`JsValue` alone is not the cause.** A controlled benchmark of the exact
  `point.line/column/offset` shape compiles to Terser-grade output either way —
  `function q(a,c){let b=0;while(b<c)a.column++,a.offset++,(a.column|0)>80&&(a.line++,a.column=1),b++;return a}`
  — and the untyped spelling is *smaller* (126 vs 131 bytes).

So the 68,673 are single-use values whose consumer is **not** adjacent: an
observable instruction sits between producer and consumer, and nesting would
reorder two effects. Closing this needs instruction scheduling (sinking a
producer toward its consumer when the crossing is provably non-interfering),
not another peephole.

## `assume_pure_property_reads` — the coercion-hook assumption

The store census said the dominant reason a value takes its own statement is
the `unstable` taint, and the taint's largest source is one arm of
`op_evaluation_is_observable`: a dynamic member read is a **coercion hook**,
because a getter could run user code while the value is being evaluated. Every
`JsValue` read is dynamic, so the taint saturates and three-address code
follows.

Terser does not make that assumption — its `pure_getters` default treats
property reads as clean, which is why it can nest where we cannot. So the fix
is not a fold: it is to let a port *state* that its objects are plain data, and
to score the claim.

`javascript.assume_pure_property_reads` (default **false** — a library cannot
assume its callers' objects have no accessors) threads through
`op_evaluation_is_observable_assuming` to every stability and fusion site.
Measured per port, each gated on its own suite:

| port | before | after | delta | tests |
|---|---|---|---|---|
| katex | 71,674 | **69,848** | **−1,826** | 1,013/1,013 |
| remark-parse | 27,571 | **27,089** | **−482** | 12/12 |
| from-markdown | 27,491 | **27,051** | **−440** | 740/740 |
| micromark | 26,683 | **26,278** | **−405** | 1,927/1,927 |
| rehype | 63,496 | **63,309** | **−187** | 136/136 |
| **total** | | | **−3,340** | |

Not enabled on two ports, each for its own measured reason:

- **`remark-math` +11.** The assumption costs bytes there; it stays off.
- **`remark` −378 but 17 failures.** This is the interesting one. The port is
  plain data — `mdast-util-to-markdown` options have no accessors — so the
  assumption is *sound* and the failure is ours: fenced code renders as
  indented (`'    a\n'` instead of "```\\na\\n```\\n"), i.e. the `fences` option
  read takes the wrong value. A read moved across its own update — the
  `ident-02` class — surfaced, not caused, by allowing more fusion. Fixing it
  is worth remark's −378 and removes a latent reorder bug that today only hides
  because the taint suppresses the fusion that would expose it.

Raw bytes move the *opposite* way on this change (micromark 90,534 → 91,527)
while Brotli falls. It is a clean example of the objective disagreeing with raw
size, and of a representation decision that has to be measured rather than
assumed.

## The `!1` precedence bug in `fold_negated_conditional_arms`

Enabling `assume_pure_property_reads` on `remark` broke 17 tests: fenced code
rendered as indented, `'    a\n'` instead of "```\\na\\n```\\n". Diffing the
emitted `formatCodeAsIndented` against the good build isolated it exactly:

```js
good:  function qb(a,b){return !1!==ra(b).fences ? !1 : (…)}
bad:   function qb(a,b){return  1!==ra(b).fences ? (…) : !1}
```

`fold_negated_conditional_arms` rewrites `!C ? A : B` into `C ? B : A`. Its
guard only checked that the condition *begins* with `!`:

```rust
let condition_is_complete_negation = tokens
    .get(condition_start)
    .is_some_and(|token| token.text == "!")
    && condition_start + 1 < question
    && …not preceded by && || ??;
```

But `!` binds tighter than every binary operator, so in `!1 !== x` the `!`
negates only the literal: the condition is `(!1) !== x`, never `!(1 !== x)`.
Dropping the `!` produced `1 !== x`, which takes the opposite branch for every
value of `x` except `1`.

Fixed with `leading_negation_covers_condition`: reject when any **top-level**
binary operator appears inside the condition, using the existing
`binary_operator_tightness` table rather than another hand-list. Two regression
tests: the `!1 !==` shape must not fold, and a genuine whole-condition negation
must still swap its arms.

The bug predates this work — it was latent because the coercion-hook taint
suppressed the fusion that exposed it. Every port was rebuilt after the fix:
micromark, remark-parse, from-markdown, rehype, remark-math and remark-rehype
are byte-identical, so the restriction costs nothing.

### Extending the assumption to `op_can_defer` does not work

After `assume_pure_property_reads` the store census on micromark moves from
`unstable=68,673` to `56,864` (−17%) — still the largest bucket. The reason is
that `unstable_values` has a second condition, `!op_can_defer(op)`, and
`op_can_defer` is an allowlist that does not contain `IndexGet`,
`RecordFieldGet` or `FieldGet`. So a property read stays unstable even once it
is no longer a coercion hook.

Completing the assumption there looks natural and is wrong:

| port | delta | tests |
|---|---|---|
| micromark | −88 | 1,927/1,927 |
| from-markdown | −29 | 740/740 |
| remark-parse | −21 | 12/12 |
| react-markdown | +58 | 93/93 |
| **rehype** | **+256** | **83/389 — 53 failures** |
| **remark** | −73 | **461/494 — 33 failures** |

`op_can_defer` governs the **expression cache**, not fusion, and the cache does
not flush reliably enough on writes to the object being read — so the read
crosses its own update. The stricter allowlist is a real safety net, exactly as
its comment claims ("`op_can_defer` is intentionally stricter because it also
governs open-ended expression caching"). Reverted; the gains were ~130 Brotli
against two broken ports.

The remaining `unstable` mass is therefore reachable only by making the
expression cache's write-invalidation precise enough to be trusted, which is
the same `ident-02` debt as the sinking work.

## `JS.call` had an arity cap, and the ports worked around it

katex emitted **365 `.apply(void 0, […])` calls**; official emits none:

```js
ours:      a.apply(void 0,["math","main","rel","≡","\\equiv",b]);
official:  a("math","main","rel","∥","\\parallel");
```

The workaround was in the port source, but the port was working around the
compiler. `JS.call` carried `require_arity(2..=7)` — callee, `this`, and at most
**five** arguments. `defineSymbol` takes six, so `js2lil` built a `JS.array` and
routed the call through `apply`. Lowering forwards `values[1..]` verbatim into a
generic intrinsic, so the ceiling was a spelling limit and nothing else.

Lifted on `JS.call`, `JS.construct` and `JS.invoke`. `JS.array` and `JS.object`
were already variadic; every remaining `require_arity` is an exact arity for a
genuinely fixed-arity builtin. `require_arity` now says "at least N" instead of
"2 to 18446744073709551615".

### A near-miss worth recording

The first conversion script computed deletion offsets against the pre-substitution
text and applied them after substitution. It spliced three lines mid-token and
**silently dropped two `defineSymbol` entries** (`\checkmark` and Greek `Κ`).
katex's 1,013 tests do not cover every symbol, so this would have shipped. It was
caught by diffing full argument tuples against `git show HEAD:src/symbols.lil`
(646 vs 642), not by the suite. Any bulk source rewrite needs a parity check
against the previous text, not just a green suite. The corrected converter lives
at `scratchpad/convert-apply.py` and runs substitution and deletion as separate
passes over freshly computed offsets.

call through `JsValue` host helpers.

## katex data tables, and three bugs that conversion exposed

State-bag → captured locals remains **REJECTED** (−2 Brotli on micromark and it
broke streaming). The remaining katex mass was nested `newArray()` + `JS.push`
and `emptyObject()` + field assigns in module-level tables. Those are the same
program as `JS.array` / `JS.object` literals; the peephole
`fold_fresh_empty_array_pushes` cannot see them because temps sit between the
allocate and the pushes.

Converted in `katexlil` (module-level only; function bodies left as sequential
stores). Elided `JS.string` when the receiver is already a string
(`js_string_of_a_string_is_the_string`).

| | raw | Brotli-11 | Δ Br vs 69,624 | vs official 62,683 |
|---|---:|---:|---:|---:|
| before this pass | 300,849 | 69,624 | — | +6,941 |
| after, 1013/1013 | **284,879** | **67,002** | **−2,622** | +4,319 |

`.push(` in esm 438 → 210. Official tests **1013/1013**.

Three miscompiles blocked the first landing:

1. **`fold_assignment_guards` used a comma-sequence as the `if` condition.**
   `f=d<t,c=parse();if(f)` became `if(f=d<t,c=parse())`, whose value is `c`.
   katex `parseArguments` then pushed every required argument into `optArgs`.
   A top-level comma in the assignment statement now refuses the fold.
   Tests: `assignment_guard_does_not_test_a_comma_sequence`,
   `a_comma_sequence_assignment_is_not_an_if_condition`.

2. **`mangleable_internal_js_key` treated `"_"` as an internal `foo_` name.**
   `JS.object("_", true)` emitted `{g:true}`; `implicitCommands[token.text]`
   still looked up `"_"`. The convention now requires `name.len() > 1`.
   Test: `a_lone_underscore_object_key_is_not_mangled`. Sequential
   `o["_"]=true` had not hit this because `"_"` was already in the stable set.

3. **`macros = _macros` was dropped, MacroExpander still read the alias.**
   The filled table was exported as `Cc as macros`; the constructor did
   `new Namespace(me, …)` with `me` still `void 0`, so every macro was an
   undefined control sequence. `macros.lil` now exports `_macros as macros`
   with no copy. Same pattern is safe in `functions.lil` / `environments.lil`
   because those assigns sit next to the export and were kept.
