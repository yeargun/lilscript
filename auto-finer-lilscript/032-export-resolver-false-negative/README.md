# 032 — mobxlil's missing classes are a false negative in our own export resolver

**Status: DIAGNOSED, WORTH 769 BROTLI, NOT YET FIXED. The rejected artifact is valid — node runs it.**

## The prize

Run the peephole pipeline over the artifact mobxlil actually ships:

| | bytes | `class` | Brotli |
|---|---:|---:|---:|
| `dist/mobx.esm.js` as shipped | 63493 | **0** | 15943 |
| the same file through the pipeline | 56444 | **10** | **15174** |
| | −7049 | +10 | **−769** |

Ten classes — [018](../018-mobx-admission-regression/README.md)'s ten — and **769 Brotli**, three
times the 253 that hypothesis estimated. mobxlil's whole remaining gap is +3007, so this is a quarter
of it sitting in a transform the compiler already performs and then throws away.

## Why it is thrown away

Tracing `apply_selected_canonical_peephole`:

```
CANONICAL: rejected at admission: generated JavaScript parser failed:
  unresolved generated export binding at generated byte 56436
```

Byte 56436 is `n as override`, the last entry of the export clause. `generated_javascript_export_witnesses`
asks `BindingResolution` to resolve `n`, gets `Resolution::Unbound`, and refuses the artifact.

## The artifact is valid

`BindingResolution` is wrong, and this is not an inference:

- `node --check` passes. (Verified it *does* catch this class of error: `var a=1;export{a as x,zzz as y}`
  is reported as an undeclared export.)
- `esbuild` bundles it.
- **node imports and runs it**: `import {override} from "./mobx-pipe.mjs"` prints `override resolved: object`.

So we are discarding a correct, 769-byte-cheaper artifact because our own resolver cannot find a
binding that three real JavaScript implementations find without difficulty.

## Where the binding actually is

The peephole deletes the alias `var Fn=n` and rewrites the clause to export `n` directly. `n` is a
top-level `var` declarator — the last one in a long list:

```js
var Da=function(e,a=He,t=He){...},ha=0,Ua=1,
    ot={value:"action",configurable:!0,writable:!1,enumerable:!1},
    n=Object.getOwnPropertyDescriptor(function(){},"name");
```

This shape is created by `merge_adjacent_declarations`, which folds consecutive `var` statements into
one declarator list — so the fold that saves bytes produces the shape the resolver then fails on.

**But the shape alone does not reproduce it.** A new test pins five forms — a declarator after a
function, object, class and arrow initializer, and the plain case — and all five resolve. So does the
284-byte mobx statement above, extracted verbatim and tested on its own. The false negative needs the
surrounding 56 KB, which means it is not "this syntax is unhandled" but scope attribution drifting
somewhere earlier in the file.

## Why this matters beyond mobx

This is the second admission false-negative found in two hypotheses, and they are the same shape: a
validator that fails closed, refuses a good artifact, and reports nothing a size measurement would
notice. [031](../031-admission-blocks-the-class-rewrite/README.md) was the property census counting a
class's own `constructor`; this is the binding resolver losing a declarator. Both refuse the *class
rewrite* specifically, which is why 018 saw its ten classes vanish and could not find a rejection —
it was counting at the wrong gate, and there were two gates.

## Next

Find where `BindingResolution` drops the declarator, with the full artifact as the reproducer:
`/tmp` copies are not durable, so the reproducer is regenerated by running the pipeline over
`mobxlil/dist/mobx.esm.js`. The fix is worth 769 Brotli on mobxlil alone, and every port that ships a
class-shaped module is behind the same gate.

The guard test added with this hypothesis — `export_binding_resolves_after_a_brace_initializer` —
pins the forms that already work so a fix cannot regress them.
